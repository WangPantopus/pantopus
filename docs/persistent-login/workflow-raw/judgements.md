=== JUDGE ===
WINNER: Pantopus Anchor — thin device-bound sessions with remembered accounts (Design 3)

SCORES:
- Anchor: device-anchored sessions and a trusted-device registry (Design 1): sec 8 conv 7 feas 5 = 20
  Deepest control set: binding happens ONLY at credential issuance (login/oauth/resume/redeem) so a stolen access+refresh pair can never be re-bound to an attacker key; separate non-biometric K_dev (DPoP) and biometry-bound K_step (server-verified presence, biometryCurrentSet/setInvalidatedByBiometricEnrollment); per-session status rows + sessions_revoked_before; DPoP nonce + jti; App Attest/Play Integrity/key attestation; Block Store grant redeems into a downgraded 'restored' session that cannot move money; reuse -> notify + force L2. Penalties: (a) the 'device-credential grant' (mode:reissued via magiclink) turns K_dev+K_step into a permanent credential and, as written, password change/reset/lockdown only revoke sessions and set require_step_up, so an attacker-enrolled trusted device (one phished login) can silently reissue itself after the victim changes/resets the password; (b) refresh pre-check by session_id is optional ('fall back to post-check'), letting an attacker with a stolen token pass DPoP against their own device row and burn the victim's session at GoTrue; (c) K_step is biometrics-only so passcode-only / no-strong-biometric users lose L2 and device-key step-up; (d) jwt_expiry 900s is project-wide and collides with the known Next middleware bug (clears cookies on expired access before refresh) -> web breakage; (e) LISTEN/NOTIFY needs a direct pg connection (not the Supavisor transaction pooler); (f) 8 new tables, nonce dance, three attestation verifiers, step-up JWTs, shared-store limiters — the largest attack surface and multi-quarter scope for a small team.
- Welcome Back — device-bound persistent sessions with 'Continue as X' (Design 2): sec 6 conv 9 feas 5 = 20
  Best UX (silent iOS reinstall, one-tap Android, OS credential sheets, account switching, own passkeys + Android Restore Credentials) and several excellent mechanics: refresh_token_hash/prev_hash lookup (fail-to-save tolerance without regexing GoTrue errors), trust levels with per-level policy, security_prefs (requireUnlockOnReinstall/allowRestoreGrants), socket kick, structured 401/403 codes, notification dedupe. Penalized on the judge's lens: (a) silent 0-gesture reinstall restore is the least safe restore path of the three (delete-app-as-logout mental model, resold/handed-over device inside 30 d) and leans hardest on undocumented Keychain survival; (b) POST /api/auth/device/enroll (verifyToken only, client-generated device.id, 'key rotation' allowed) lets anyone holding a stolen 1-h access token bind the session to their own key and, on Android, receive a restore grant -> persistent access; (c) PROOF_REQUIRED enforcement keyed off the client-controlled X-Client-Platform version header lets a stolen unbound token claim an old app version; (d) restore grant is cloud-backed (setShouldBackupToCloud=true) and redeems into a full-power bound session (only >60 d triggers step-up) — Google-account + old-device-PIN compromise becomes Pantopus takeover with no Pantopus credential; (e) drops the getUser round trip after soak, so GoTrue-side revocations/bans become invisible until the registry catches up; (f) own WebAuthn RP + Restore Credentials + local JWT verify + everything else — scope comparable to Design 1.
- Pantopus Anchor — thin device-bound sessions with remembered accounts (Design 3): sec 7 conv 7 feas 8 = 22
  Smallest correct core: one AuthDevice registry keyed by (device_id, key thumbprint) with current_session_id, ES256 DPoP required on /refresh (pre-check row, post-check JWT session_id), sessions_valid_after watermark, revoke_auth_session RPC, immediate revocation by keeping the existing getUser round trip (session_not_found once the auth.sessions row is gone), 90-day inactivity, hashed single-use resume grants that are same-device/D2D only (no cloud), 'reinstall is never Level 1 and never a wipe', no OS lock -> no L2, no reissue path on iOS (revoked means re-login), legacy adoption explicitly bounded and flag-gated with kill switch, keeps jwt 3600 and existing TokenAuthenticator/KeychainStore/TokenStorage. Holes (all fixable, some shared with Design 2): (a) POST /api/auth/devices/register (verifyToken + attacker's own DPoP, 'idempotent upsert') plus the 'current_session_id IS NULL -> adopt' rule lets a stolen access token enroll an attacker device on the victim's account, adopt the session on next refresh and, on Android, receive a resume grant; (b) key_backing/biometric are client-claimed until Phase 3 attestation, yet key_backing gates grant redemption; (c) L2 gate is a boolean LAContext/BiometricPrompt (not cryptographic) and step-up key only arrives in Phase 3; (d) unauthenticated /logout scope=local acts on deviceId (clears binding, deletes push tokens, revokes grants); (e) no per-session rows -> web sessions invisible until Phase 4, no 'restored' downgrade; (f) in-memory rate limits/jti. Wins on total because its restore semantics are the most conservative, its revocation is immediate, and it is the only design a small team can ship end-to-end; the deeper controls of Design 1 graft cleanly onto it.

GRAFT:
- From Design 1 — bind-at-issue-only rule: device key binding and resume-grant minting happen ONLY inside credential-issuing flows (login, oauth/callback|token|native, resume/redeem); no bearer-only endpoint may create or rotate a binding. /devices/register is reduced to metadata + push-token linkage for the device whose thumbprint already matches the session's binding (DPoP verified against the stored key).
- From Design 1 — refresh pre-check by session: client sends the (possibly expired) access token or sessionId with the refresh; server resolves session -> bound device -> stored JWK and verifies DPoP against THAT key before calling GoTrue (no 'find device by client-supplied deviceId, check user afterwards'); post-check session_id equality stays as defense in depth.
- From Design 1 — K_step (biometry-bound SE/Keystore key: .biometryCurrentSet / setUserAuthenticationRequired+setInvalidatedByBiometricEnrollment) used to sign the L2 resume challenge and /api/auth/step-up {device_key}, so 'Continue as X' presence and Tier-2 step-up are server-verified rather than a client boolean; add a userPresence/DEVICE_CREDENTIAL-gated fallback key for passcode-only devices so L2 is not lost.
- From Design 1 — 'restored' session context: any session minted from a Block Store grant (or any non-interactive path) is tagged restored and cannot perform step-up-protected actions (payouts, password/email change, device revocation, account deletion) until a password/passkey/native-IdP credential is presented once; flips to interactive afterwards.
- From Design 1 — TOKEN_REUSE / DEVICE_MISMATCH / device-removed / new-device / password-changed security events with email + push to the user's other devices, an 'account lockdown' action (revoke all + revoke grants + require interactive login everywhere), and best-effort silent 'session_revoked' push before push tokens are deleted (client must confirm with a 401 before wiping).
- From Design 1 — rate limiting keyed per device thumbprint / per account in a shared store (rate-limit-redis or Postgres) for /refresh, /resume, /step-up, /challenge; TTL-pruned jti table or Redis SETNX; App Attest re-attestation on iOS reinstall as part of the resume request.
- From Design 2 — auth_session rows keyed by JWT session_id (device_id nullable for web) with refresh_token_hash + prev_refresh_token_hash: enables lookup without an access token, tolerates fail-to-save without regexing GoTrue error text, lists web sessions in 'Where you're logged in' from Phase 1, and gives per-session revoke_reason/last_seen.
- From Design 2 — trust levels (trusted / unverified / suspect) with per-level policy: unverified (no attestation, GMS-less, simulator) devices get no resume grants and a 30-day inactivity window; suspect (reuse, 2x PROOF_INVALID, appAccessRisk) revokes and forces interactive login; attestation degrades trust, never hard-blocks login.
- From Design 2 — security_prefs on the user (requireUnlockOnReinstall, allowRestoreGrants, newDeviceEmail) with grant revocation on opt-out; restore-grant step-up after 60 days; 'Not you?' deep link in the new-device email to the Devices page; new-device notification dedupe when lineage is proven (resumed_from_device / same model within 30 d).
- From Design 2 — Phase 0 polish items: structured 401 codes parsed everywhere plus a 403 STEP_UP_REQUIRED interceptor that performs step-up and retries once; Compose autofill ContentType hints, iOS .username + performAutoFillAssistedRequests, asset_statements meta-data, telemetry SLOs (session_restore_ok{path,reinstall}, proof_invalid rate, revocation p99).
- From Design 2 — socket-side kick: emit auth:session_revoked to the user's room and disconnect sockets matching the revoked session_id, in addition to Design 3's getUser-based HTTP revocation.

CONCERNS:
- Session re-binding hole: POST /api/auth/devices/register (verifyToken + the caller's own DPoP, 'idempotent upsert') combined with the refresh rule 'current_session_id IS NULL -> adopt' lets an attacker holding a stolen 1-h access token (+ refresh token) enroll a fresh device row on the victim's account, adopt the session on the next refresh and, on Android, receive a resume grant (persistent access). Fix: bind only at issuance; register may not create rows or set current_session_id; adoption only for sessions issued before the binding cutoff (record bound_at_issue), and never mint grants outside login/resume.
- Refresh pre-check scoped by client-supplied deviceId, not by the token's session: server should resolve session_id/user first (from the expired access token, sessionId, or refresh_token_hash) and verify DPoP against the key bound to THAT session before calling GoTrue; otherwise an attacker with a stolen token and their own row passes DPoP and burns the victim's session (DoS) and cross-user device_id collisions are possible.
- Client-claimed trust inputs before Phase 3: keyBacking (used to reject software keys on /resume) and the biometric gate are asserted by the client; move Android key attestation chain verification (cheap, arrives with the key) into the same phase as resume grants, or treat all pre-attestation redemptions as 'restored' with money/credential actions gated by password/passkey.
- L2 gate is a boolean (LAContext / BiometricPrompt without CryptoObject) — fails MASWE-0022 spirit for the reinstall path; add the biometry-bound K_step signature to the resume request (with a passcode/DEVICE_CREDENTIAL-gated fallback key) so presence is server-verified, and use the same key for /step-up from Phase 2 instead of Phase 3.
- Unauthenticated POST /logout scope=local with deviceId clears bindings, deletes PushToken rows and revokes grants — require proof (valid access token whose session is bound to that device, or refresh token + DPoP) before any side effect on the device row; keep unauthenticated behaviour limited to cookie clearing.
- No per-session rows: one current_session_id per (user, device) cannot represent web sessions, two sessions on one device, or per-session revoke reasons; add auth_session rows keyed by session_id (Design 2) so 'Where you're logged in' and revoke-others cover web from Phase 1.
- No downgraded 'restored' context: a Block Store grant + client-claimed key + client-side biometric mints a full-power session; tag grant-minted sessions restored and require an interactive credential once before payouts, password/email change, device revocation, or account deletion.
- In-memory express-rate-limit and a Postgres AuthDpopJti with no pruning job: with >1 backend instance per-IP/per-grant limits and jti replay checks weaken; move to a shared store (Redis or Postgres with TTL prune) before enforcement (AUTH_DEVICE_BINDING=required).
- Step-up token is a bare HMAC(userId|sessionId|exp): add jti + purpose and one-shot consumption for delete_account / device revocation, and require the K_step (biometryCurrentSet) method or password — never a plain LAContext boolean — for step-up.
- TOKEN_REUSE branch identifies the device from the request's deviceId; in optional mode a replay without DPoP would revoke only the session — define that the legit device (found via the session's binding) is notified and forced to L2/L3, and that the regex on GoTrue error text is replaced by refresh_token_hash/prev_hash tracking or the sb-auth-refresh-token-reuse headers.
- Legacy adoption window (optional mode) is a stated status-quo risk but should be bounded explicitly: cut over by app version, force legacy sessions to re-login within N days, and never allow adoption for sessions issued after the client shipped DPoP.
- Web parity gaps left open (Next middleware clears cookies before refresh; web sessions absent from Devices list until Phase 4) — pull web session rows and the middleware fix into Phase 1/2 so 'sign out everywhere' is truly everywhere.
- Privacy/compliance follow-through is listed but not sequenced: device id, device model, IP/geo, Block Store payload and hardware key material must be added to docs/compliance/privacy-data-inventory.md and store labels BEFORE the Phase 1 store submission, with retention limits for AuthSecurityEvent and revoked rows.

LOAD-BEARING CLAIMS:
- GoTrue auth.getUser(jwt) fails (session_not_found / 403) once the auth.sessions row referenced by the JWT session_id claim is deleted — this is what makes Design 3's per-device revocation immediate; verify on the hosted project's GoTrue version (and confirm supabase-js surfaces it as an error the middleware turns into 401).
- A SECURITY DEFINER function owned by postgres can DELETE FROM auth.sessions on hosted Supabase (auth schema is owned by supabase_auth_admin) and the delete cascades to auth.refresh_tokens; Supabase support/operational stance on touching auth.* directly.
- JWT session_id claim is present in every access token and stays constant across refresh rotation (so current_session_id / auth_session.id survive rotations); confirm on the project's refresh-token algorithm version (v1 parent-token vs v2 counter) and whether sb-auth-refresh-token-reuse headers are returned instead of the regexed 'already used|not found' messages.
- admin.generateLink({type:'magiclink'}) + verifyOtp({type:'magiclink', token_hash}) mints a real session (with session_id) without sending email, on the hosted project, and is not blocked by OTP rate limits; side effects (email_confirmed_at, last_sign_in_at, amr=otp) are acceptable.
- iOS Keychain items with kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly / non-synchronizable — including the Secure Enclave key dataRepresentation — survive app uninstall/reinstall on iOS 17/18/26 for the same Team ID (undocumented; last DTS confirmation iOS 17.5); and the install marker in Application Support with isExcludedFromBackup is reliably absent after reinstall.
- SecureEnclave.P256.Signing.PrivateKey with SecAccessControl .biometryCurrentSet (K_step) is invalidated on Face ID/Touch ID re-enrollment and destroyed when the passcode is removed; LAContext .deviceOwnerAuthentication semantics on passcode-only devices; App Attest keys do not survive reinstall and attestKey is not rate-limited per key beyond Apple's fleet-wide guidance.
- Android Keystore keys are wiped on uninstall (PackageManager clearKeystoreData) so a new AuthDevice row per install is correct; StrongBox availability and key attestation chain (Google roots incl. the 2026-02 root, CRL) can be verified server-side; setUserAuthenticationRequired + setInvalidatedByBiometricEnrollment behave as assumed with BiometricPrompt CryptoObject.

- Play Integrity standard requests: default 10k/day quota vs expected enrollment/resume volume, requestHash binding, MEETS_DEVICE_INTEGRITY availability on the OEM long tail; Google Cloud project linkage in Play Console.

- Supabase signs access JWTs with HS256 (SUPABASE_JWT_SECRET) vs ES256/JWKS on this project — needed if any local decode/verify is added; the unverified decode-after-getUser used by Design 3 is safe only because getUser already validated the token.
- GoTrue refresh rotation tolerances (10 s reuse interval, parent-token fail-to-save grace) hold on the hosted project so a client crash between server rotation and local persist does not trigger TOKEN_REUSE.
- auth.admin.signOut(jwt,'others'|'global') requires a currently valid access JWT of that user; verify behaviour with expired JWTs and confirm it revokes all sessions including those minted via magiclink.
- Supabase [auth.sessions] inactivity_timeout / single_per_user are Pro-plan features — Design 3's 90-day inactivity is enforced at our /refresh, so confirm nothing else depends on GoTrue session controls.
- signInWithIdToken for apple/google requires the Apple Services ID / native client IDs configured as audiences on the project; Apple Team ID (project.yml DEVELOPMENT_TEAM blank) and Play App Signing SHA-256s exist for regenerating AASA/assetlinks; Apple's CDN can fetch the AASA from pantopus.com apex + www without redirects.
- The backend runs (or will run) as more than one instance — determines whether express-rate-limit MemoryStore and the AuthDpopJti table are sufficient or a shared store is required before enforcement.
- APNs/FCM silent 'session_revoked' pushes are best-effort only (throttled, not delivered when force-quit); revocation must never depend on them.
- The existing express `pg` dependency can open a direct (non-pooler) connection if LISTEN/NOTIFY or a revocation cache is grafted later; Supavisor transaction mode does not support LISTEN.
=== JUDGE ===
WINNER: Welcome Back: device-bound persistent sessions with Continue as X

SCORES:
- Anchor: device-anchored sessions and a trusted-device registry: sec 9 conv 6 feas 4 = 19
  Strongest security story (two SE/Keystore keys, DPoP with server nonce, App Attest + Play Integrity + key attestation, restored-context sessions that cannot move money, LISTEN/NOTIFY revocation, 15-min access tokens, lockdown). But it pays for it in UX and scope: iOS reinstall is never zero-gesture and needs a biometry-bound K_step (users without Face ID enrolled, or after a Face ID re-enrol, drop to a full login), 30-day dormancy forces re-gating, a 428 nonce dance adds a round trip to refresh, password reset kicks the requesting device, and jwt_expiry=900 quadruples refresh traffic and touches the already-fragile web refresh path. Eight new tables, three attestation verifiers, a Postgres NOTIFY bus, ES256 step-up JWTs and four new client-side keys/services is far beyond what a small team ships in the stated ~13 weeks; the phasing is sound but Phase 2/3 are each a quarter of work.
- Welcome Back: device-bound persistent sessions with Continue as X: sec 8 conv 9 feas 6 = 23
  Hits the Instagram/YouTube bar: iOS delete→reinstall→open→in (0 gestures, gated only when app lock/‘require unlock’/stale), Android one-fingerprint Continue-as via Block Store, account remembered after sign-out, OS credential sheets (AutoFill/passkey/SIWA/Credential Manager) as the universal fallback, and the clearest enumeration of first-launch UI states (A–E per platform). Security is solid: session registry keyed by session_id, refresh_token_hash+prev_hash lookup, DPoP with rth/did binding on /refresh, revocation ≤15 s incl. socket kick, cryptographic step-up, trust levels as signal not gate. Weak spots: silent iOS reinstall and a cloud-backed restore grant that redeems into a full-privilege session (Google-account takeover + attacker biometric on attacker device passes every gate), and Phase 3 (own WebAuthn RP, Restore Credentials, account switching, local-JWT migration) is oversized. Reuses AuthManager/AuthRepository (adds one state + a coordinator), keeps 1 h access tokens and web policy unchanged, and Phases 0–2 are independently valuable.
- Pantopus Anchor: device-bound sessions with remembered accounts: sec 7 conv 7 feas 8 = 22
  Most shippable: smallest schema (5 tables + 2 columns, correctly numbered 160), one device key, keeps the existing per-request getUser as the immediate revocation authority (delete auth.sessions row → session_not_found), HMAC step-up token in the same style as the CSRF secret, grant minted in an idempotent /devices/register so /login stays platform-neutral, explicit reuse of KeychainStore/TokenStorage/TokenAuthenticator, and it is the only design that names the GoTrue-direct-call bypass. Security is a notch lower because biometry-bound step-up, attestation and enforcement all land in Phase 3, DPoP proofs are not bound to the refresh token (no rth), and the optional-mode ‘adopt legacy session’ window is real. Convenience is a notch lower because reinstall always costs a gesture (passcode fallback allowed, which is good), an explicit sign-out demands a password again, and native SIWA/Google/passkeys arrive late; the UI states are specified but thinner than Welcome Back's.

GRAFT:
- From Anchor: give sessions minted from a restore grant a `restored` context (auth_method=restore_grant) and record `step_key_enrolled_via` (interactive|restore); a restored session can browse/chat but payouts, password/email change, device revocation, passkey add and device-key step-up require a password/passkey/native-SIWA once, which flips it to interactive. This closes the Google-account-takeover + cloud-restore hole without touching the happy path.
- From Anchor: on TOKEN_REUSE / repeated PROOF_INVALID set `require_step_up=true` on the device (forcing the biometric Continue-as card) instead of only marking it suspect and hard-revoking, so the legitimate owner recovers with one gesture while the attacker (no device key / no biometric) cannot; keep the email+push notification.
- From Anchor: accept an optional (possibly expired, signature-verified) accessToken in /refresh so the registry row can be found by `session_id` when the refresh_token_hash/prev_hash lookup misses (double fail-to-save, partial DB write after GoTrue rotated); never treat a hash miss on a known session as ‘legacy/unbound’.
- From Anchor: best-effort remote wipe — send a silent push {type:'session_revoked'} to the revoked device's push tokens before deleting them; the client honours it only after confirming with GET /api/auth/sessions (401 SESSION_REVOKED).
- From Anchor: per-device-thumbprint rate limits on /refresh, /restore, /step-up and a single-use TTL `auth_challenge` table; keep the install sentinel as a downgrade signal (already in WB) and move the App-Lock preference to Keychain/encrypted prefs (WB does this) plus mirror it on the device row.
- From Pantopus Anchor: keep `supabase.auth.getUser` per request as the revocation authority (deleting the auth.sessions row makes it fail immediately) and only add a local claims decode for session_id/iat + the registry/`sessions_revoked_at` check; defer the local-JWT-verification migration and the ‘drop getUser’ step to a later hardening phase so banned/deleted users and GoTrue-side revocations are never missed by a 15 s cache.
- From Pantopus Anchor: mint/re-issue the Android restore grant (and link the push token to the device) in an idempotent `POST /api/auth/device/enroll|register` called after login, on app update and on FCM rotation, rather than in every login/oauth response — keeps /login, /oauth/* and /refresh shapes platform-neutral for old clients.
- From Pantopus Anchor: hard rule that a device with no OS lock (LAContext.canEvaluatePolicy(.deviceOwnerAuthentication)==false / BiometricManager != SUCCESS) gets neither silent L1 reinstall restore nor L2 resume — it goes to L3 (OS credential sheet). Also allow passcode fallback for the Continue-as gate (deviceOwnerAuthentication / DEVICE_CREDENTIAL) — do not require biometrics for restore.
- From Pantopus Anchor: enforce a sliding inactivity window (90–180 d since last successful refresh) in our own registry at /refresh so it does not depend on the Supabase Pro `[auth.sessions] inactivity_timeout`; treat the Supabase setting as defence in depth only.
- From Pantopus Anchor: explicitly document and verify the GoTrue-direct bypass (anyone holding the Supabase URL + anon key + a refresh token can call /auth/v1/token and skip our DPoP proxy); make ‘anon key never ships in a client bundle’ a stated invariant with a CI grep, and note that hosted Supabase cannot network-restrict GoTrue.
- From Pantopus Anchor: exclude the Android `device_identity` prefs (deviceId/installId) from backup/D2D so a device id never follows a backup; regenerate deviceId together with the Keystore key; number the migration 160_auth_devices.sql (159 is the current head) and reuse the already-present `jsonwebtoken`/`pg` deps before adding jose.
- From Pantopus Anchor: ship the web `/app/settings/security` devices page (cookie transport + CSRF) in the same phase as the mobile Devices screens, and fix the Next middleware clear-cookies-before-refresh gap in Phase 1 rather than leaving it as an open question, so web/mobile session semantics stay consistent.

CONCERNS:
- Cloud-backed Block Store restore grant redeems into a full-privilege session: an attacker who takes over the Google account and restores to their own device passes Play Integrity, satisfies BiometricPrompt with their own biometric, enrols a fresh step-up key and can then pass device-key step-up for payouts. Fix: default `setShouldBackupToCloud(false)` (same-device + D2D only) with cloud as an explicit opt-in, mint restored sessions with a `restored` context that requires password/passkey/native-SIWA once before money/credential changes or step-up-key enrolment, and always send the new-device email on redemption when installId/model differ.
- Silent iOS reinstall restore has no server-visible presence check and no re-attestation gate: the design re-attests App Attest ‘lazily’ after reinstall while trust_level and restore-grant issuance continue as before. Fix: require the re-attest to succeed before reissuing restore grants or accepting device-key step-up on that install, require an OS lock for silent restore, and make the decision (silent vs gated) an explicit, documented product default with the `requireUnlockOnReinstall` toggle discoverable in Security settings.
- `POST /api/users/logout` is described as ‘optional Bearer’ yet accepts scope others|global — those scopes must require verifyToken (+CSRF for cookie transport) and step-up; only scope local may stay unauthenticated best-effort as today.
- Refresh lookup by refresh_token_hash alone is brittle: if GoTrue rotates but the registry write fails, or two fail-to-saves happen, the next refresh misses both hashes and, in enforce mode, returns PROOF_REQUIRED and signs the user out. Add the session_id fallback (expired access token in body), make the GoTrue-refresh + registry-update path idempotent/retried, and reconcile via the new token's session_id rather than dropping the user.
- Dropping the remote getUser after ‘soak’ removes the only check for banned/deleted users and GoTrue-side revocations until exp, and the 15 s in-process cache is per-instance. Keep getUser (it is already paid today) or add a distributed revocation cache before removing it.
- Step-up key enrolment is allowed in any session, so a key enrolled during a restore-grant or suspect session carries the attacker's biometric. Record `step_key_enrolled_via` and accept `method:'device_key'` only for keys enrolled in an interactive (password/passkey/SIWA) session; invalidate on trust downgrade.
- Client-generated `auth_device.id` upserts must be scoped by (user_id, id) and reject an id already owned by another user; otherwise a malicious client can collide with or hijack another user's device row (which drives revocation and restore grants).
- Phase 3 is oversized for a small team (own WebAuthn RP with SimpleWebAuthn, Android Restore Credentials that likely needs allowBackup changes, account switching, passkey nudges, local-JWT migration). Split it: ship native SIWA + Credential Manager Sign in with Google + AutoFill/asset links first; defer passkeys until Supabase passkeys GA (or a minimal own RP) and Restore Credentials until the allowBackup=false question is answered on device.
- New-device email dedupe (‘same model + trust within 30 d’) suppresses exactly the alert a same-model attacker would trigger; dedupe only on proven lineage (restore grant / same device key), never on model.
- Play Integrity default quota (10k/day) and StrongBox/attestation variance across OEMs will bite at enrolment of the existing user base; request quota before Phase 2 and keep attestation in observe mode until false-positive rates are measured. Likewise `setUserAuthenticationParameters` requires API 30 — minSdk 26 needs the deprecated validity-duration path or a min-API gate for the step-up key.
- Rate limiting and the jti replay table are single-instance/in-process (express-rate-limit MemoryStore; unlogged Postgres table is fine but the limiter is not); per-user limits on /restore, /step-up and /passkeys/login must be moved to a shared store before enforcement or they are trivially bypassed across instances.
- Timeline optimism: 9–13 weeks across four phases is unrealistic for the listed surface (three attestation verifiers, DPoP, registry, five new screens per platform, association-file work blocked on the unknown Team ID / Play App Signing fingerprints). Re-plan with Phase 0 + Phase 1 as the committed deliverable and the rest flag-gated.
