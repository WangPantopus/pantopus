## FACTS
- [high] iOS Keychain: items written by an app are NOT deleted when the app is uninstalled and remain readable by a reinstalled app with the same Team ID/access group. Apple DTS (Quinn) states this is an implementation detail, not an API contract: 'Our keychain documentation has never specified what would happen in this case' and 'it would not surprise anyone if the 10.3 behaviour returned'. Confirmed still true on iOS 17.5 (June 2024); no Apple statement of a change for iOS 18/26 was found.
  src: https://developer.apple.com/forums/thread/36442 ; https://developer.apple.com/forums/thread/72271 2024-06 (last Apple DTS confirmation); re-checked 2026-08-18
- [high] iOS 10.3 betas 2-5 deleted an app's keychain items on uninstall (Apple staff 'gc.' called it 'an intentional change in iOS 10.3 to protect user privacy' and said shared access-group items 'won't be deleted until those other apps have been deleted as well'); the change was rolled back in beta 6 and never shipped. So today keychain access-group items are not wiped when the last app of a team is deleted either — but the only documented Apple intent for a future wipe is 'delete when the last app in the group is gone'.
  src: https://developer.apple.com/forums/thread/72271 2017-03 (behavior); still current 2026-08
- [high] Apple's recommended way to force 'delete on uninstall' semantics is to entangle the keychain secret with a random key stored in the app sandbox (or a UserDefaults first-launch flag) and treat missing sandbox state as a fresh install.
  src: https://developer.apple.com/forums/thread/36442 2024-06
- [high] kSecAttrSynchronizable defaults to false for third-party items; when true the item syncs via iCloud Keychain to all the user's devices (passwords since early iOS; certificates and keys since iOS 14/macOS 11), and updating/deleting it affects all copies on all devices. It cannot be combined with any *ThisDeviceOnly accessibility value.
  src: https://developer.apple.com/documentation/security/ksecattrsynchronizable 2026-08-18
- [high] *ThisDeviceOnly keychain classes are wrapped with the device UID: they are included in backups but are 'useless if restored to a different device'; kSecAttrAccessibleWhenPasscodeSetThisDeviceOnly items additionally don't sync, aren't backed up, aren't in escrow keybags, and are destroyed when the passcode is removed. Non-ThisDeviceOnly items can migrate to a new device via encrypted backup/restore.
  src: https://support.apple.com/guide/security/keychain-data-protection-secb0694df1a/web 2026-08-18
- [high] Secure Enclave keys (kSecAttrTokenIDSecureEnclave / CryptoKit SecureEnclave.P256): the private key is not stored inside the SE but on the device wrapped so only the SE can use it; the keychain reference survives app uninstall/reinstall on the same device (Apple DTS: 'when I uninstall my application and install it again, the key is still available. Indeed.'), but keychain items 'do not always survive backup and restore' and SE keys never migrate to a new device, so code must handle the key disappearing.
  src: https://developer.apple.com/forums/thread/129402 2020-02 (DTS statement); behavior unchanged per 2024-2026 threads
- [high] SE keys can sign server challenges (ECDSA P-256) for device-bound proof-of-possession, and can be gated with SecAccessControl flags such as .biometryCurrentSet (item invalidated when Touch ID fingers are added/removed or Face ID is re-enrolled; iOS 11.3+) combined with .privateKeyUsage; LAContext can be supplied via kSecUseAuthenticationContext.
  src: https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/biometrycurrentset 2026-08-18
- [high] App Attest keys are unique per app installation: 'The keys that you generate remain valid through regular app updates, but don't survive app reinstallation, device migration, or restoration of a device from a backup.' You must persist the keyId (not the attestation) and generate a new key + attest again after reinstall.
  src: https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity ; WWDC21 10244 transcript 2026-08-18
- [high] App Attest attests once per key (attestKey hits Apple servers 'only once per app instance'); assertions have no limit ('There's no restriction on the number of assertions'). Apple warns about being rate limited if a large install base attests at once (ramp 1M DAU over ~a day). Server must verify: x5c chain to the Apple App Attest root CA, nonce = SHA256(authData||clientDataHash) in cert extension OID 1.2.840.113635.100.8.2, keyId == SHA256(pubkey), RP ID hash == SHA256(App ID), counter == 0, aaguid appattest/appattestdevelop, credentialId == keyId; store public key + receipt; assertions must have monotonically increasing counter and matching challenge; receipts can be redeemed for a fraud-risk metric (approx. number of keys created on that device for your app).
  src: https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server 2026-08-18
- [high] App Attest proves the key lives in Secure Enclave of genuine Apple hardware in a valid instance of your app; it does not detect a jailbroken OS ('App Attest can't definitively pinpoint a device with a compromised operating system').
  src: https://developer.apple.com/documentation/devicecheck 2026-08-18
- [high] DeviceCheck two bits: stored on Apple servers per device, shared by all apps from one developer (team), and per Apple's WWDC21 session 'The state persists across app reinstallation, device transfer between users, and even Erase all contents and settings.' Server-to-server API: POST /v1/query_two_bits, /v1/update_two_bits, /v1/validate_device_token with ES256 JWT auth; response includes last_update_time (YYYY-MM).

## CAVEATS
- Could NOT verify that Restore Credentials is 'backed by Block Store': neither the Android docs nor the Nov 2024 announcement blog name Block Store; they only say the restore key is 'stored locally and backed up to the cloud' via 'the android system's backup and restore mechanism'. Treat the Block Store linkage as unconfirmed.
- Restore Credentials is explicitly NOT a same-device uninstall/reinstall solution (uninstall deletes the restore key); it targets new-device setup/D2D transfer. Block Store is the only Google-documented same-device-reinstall persistence, and only when the user has Backup enabled.
- DeviceCheck persistence across reinstall/erase/transfer is stated in Apple's WWDC21 session transcript (and WWDC17), not on the API reference page; the reference page is silent on lifecycle.
- Apple has never documented keychain persistence across uninstall; the last explicit DTS confirmation found is June 2024 (iOS 17.5). No evidence of a change in iOS 18/26 was found, but Apple's own staff say the 10.3-style wipe could return; do not make it a hard dependency (entangle with a sandbox-stored random key if you want deterministic behavior).
- Uber's or Instagram's use of Apple App Attest could not be verified from primary sources; only Google's Oct 2025 blog naming Uber/TikTok/Stripe/Paytm as Play Integrity users was found. Instagram 'Where you're logged in' details come from third-party how-to articles (Meta help pages did not render).
- Google's Block Store doc contains an internal inconsistency ('Android 9 (API 29)'); API 28 = Android 9, API 29 = Android 10. Assume 'Android 9+' as the doc's intent but verify on target devices.
- Supabase v2 refresh-token algorithm details (counter-based tokens, allowed 'fail-to-save' reuse) come from reading GoTrue master source on 2026-08-18; the public docs still describe the v1 parent-token/10-second-interval model. Behavior on hosted projects depends on the algorithm version Supabase has enabled for the project.
- Supabase has no admin endpoint to enumerate/revoke a single user's sessions; building a 'trusted devices' UI requires querying auth.sessions directly (service role) or maintaining your own device table keyed by session_id from the JWT.
- Supabase passkeys are experimental/beta (API may change); supabase-kt has API scaffolding but no sign-in method as of 3.7.0, so a native Android passkey login against Supabase would need to call the /auth/v1/passkeys/authentication endpoints directly.
- App Attest 'attestation once per key' is Apple guidance, not an enforced per-key limit; the documented risk is service-wide rate limiting when many installs attest simultaneously (ramp gradually).
- Play Integrity Device Recall is beta and opt-in (interest form + Play Console); DeviceCheck bits and Device Recall are per-developer/per-app respectively and only 2-3 bits — enough for 'seen device / trusted device' flags, not for storing tokens.
- No API exists to 'upgrade' a Sign in with Apple credential to a passkey; iOS 18/26 automatic passkey upgrades (.conditional) only trigger after a password autofill by a credential manager, and the iOS 26 account-creation API may return preferSignInWithApple.
