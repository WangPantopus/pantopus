## SUMMARY
Android session auth is a bearer-token scheme built around three singletons in frontend/apps/android/app/src/main/java/app/pantopus/android/data/auth/. `TokenStorage` persists access_token / refresh_token / user_id / user_json in `EncryptedSharedPreferences` (file `shared_prefs/secure_auth_tokens.xml`, values AES256_GCM, keys AES256_SIV) wrapped by a Jetpack `MasterKey` with `KeyScheme.AES256_GCM` — a plain Keystore master key with no user-auth binding, no StrongBox request, no expiry tracking. That prefs file (and the legacy DataStore `datastore/auth_tokens.preferences_pb`) is excluded from Auto Backup and device-to-device transfer in both `backup_rules.xml` and `data_extraction_rules.xml`, and the manifest sets `android:allowBackup="false"`; combined with the Keystore master key being wiped on uninstall, nothing about the session survives delete+reinstall today. There is no Block Store, no Credential Manager / Sign-in-with-Google, no Play Integrity, no device-installation identifier, no per-device keypair.

At cold start `RootViewModel.init` launches `AuthRepository.restore()`, which reads the access token, loads the cached `user_json`, and calls `GET /api/users/profile` (`api.me()`) through the main OkHttp client. A 401 there is first handled by `TokenAuthenticator` (silent refresh + replay); if it still 401s (or refresh is auth-rejected) `restore()` clears storage and goes `SignedOut`. Any 403/5xx/IOException keeps the cached user and enters `SignedIn` offline-first; a transient refresh failure surfaces as `NonRetriableIOException` so `RetryInterceptor` never re-drives it. `PantopusNavHost` cross-fades Splash (state Unknown) → PlaceLaunch/AuthNavHost (SignedOut) → `AppLockHost{RootTabScreen}` (SignedIn); `AppLockManager` (BiometricPrompt BIOMETRIC_STRONG|DEVICE_CREDENTIAL, per-user boolean prefs in `app_lock_prefs`) locks the already-signed-in UI on background/resume and gates sensitive actions, but it never protects the tokens themselves and never participates in sign-in.

Refresh is a classic OkHttp `Authenticator`: `AuthInterceptor` stamps `Authorization: Bearer` + `X-Client-Platform: android` on every request; on 401 `TokenAuthenticator.authenticate` skips the refresh endpoint and un-authenticated requests, then serializes on a static `lock`, double-checks storage for an already-rotated token (single-flight), else calls `AuthRepository.refreshTokens()` which POSTs `/api/users/refresh` `{refreshToken}` on a dedicated `@Named("authRefresh")` OkHttp/Retrofit stack (no interceptors, no authenticator, avoids dispatcher deadlock/recursion). Success rotates access (+refresh if returned) via `TokenStorage.updateTokens` and reconnects the socket; HTTP 400/401 (incl. backend `TOKEN_REUSE`) → `AuthRejected` → `signOut()`; IOException/403/429/5xx → `Transient` → session preserved; a third 401 on the same request (`MAX_ATTEMPTS = 2`) also signs out. Interactive sign-in is email/password `POST /api/users/login` or browser OAuth (Google/Apple) via Custom Tabs with a `pantopus://auth/callback?app_nonce=` redirect verified in constant time by `OAuthSessionStore`, then `POST /api/users/oauth/callback` (code) or `/oauth/token` (legacy fragment). `signOut()` is local-only: clears storage, disconnects socket, resets analytics/deep-link/moderation state — it never calls the backend `POST /api/users/logout`, so the Supabase session/refresh token stays valid server-side until it expires or is reused.

## GAPS
- Nothing survives uninstall: tokens are Keystore-wrapped (master key deleted with the app) AND excluded from backup/D2D, and there is no Block Store, no Credential Manager saved-credential, no server-side device record. After delete+reinstall the user must fully re-authenticate; there is no 'Continue as X' hint (user_json is also wiped).
- No device identity primitive at all: no installation ID, no Keystore-generated per-device asymmetric key (KeyGenParameterSpec/attestation), no StrongBox, no Play Integrity, no X-Device-Id header. The backend cannot distinguish this device from any other bearer holder, so trusted-device records, per-device revocation and stolen-device handling have nothing to key on.
- Token storage is not user-auth-bound: MasterKey uses default KeyGenParameterSpec without setUserAuthenticationRequired / setUnlockedDeviceRequired / StrongBox, so a rooted device or backup of app data (if backup were ever enabled) can decrypt tokens without biometrics; AppLockManager's BiometricPrompt uses no CryptoObject and only gates UI, not key access.
- androidx.security:security-crypto is pinned at 1.1.0-alpha06 (library is deprecated by Google); any new device-bound key work needs its own Keystore/Tink code rather than extending MasterKey.
- signOut() is local-only — never calls POST /api/users/logout; the Supabase refresh token / session remains valid server-side until 7-day expiry or reuse detection. Also 'sign out from app lock' and account-deletion paths only clear local storage.
- No proactive refresh: expiresAt/expiresIn from login/refresh are discarded; refresh happens only reactively on a 401 (and never for the Socket.IO connection, which just gets reconnected after an HTTP-triggered rotation).
- Refresh single-flight is a JVM synchronized static lock inside the Authenticator; there is no cross-process (widget/FCM service) coordination and no persisted 'refresh in flight' guard, so a rotate-then-crash between server rotation and TokenStorage.updateTokens still risks TOKEN_REUSE on next launch (mitigated only by NonRetriableIOException).
- AuthRepository.restore() clears storage on ANY 401 from /profile even though TokenAuthenticator already tried refresh; there is no distinction between 'refresh token expired' vs 'this access token revoked but refresh still fine' vs backend TOKEN_REUSE code — all collapse to SignedOut with no user messaging or re-auth affordance (e.g. biometric re-login).
- Login form has no autofill/ContentType hints and no Credential Manager (passkeys / saved passwords / Sign in with Google), so even the OS-level 'minimal friction' path is missing on reinstall.
- No trusted-device / sessions management surface in the app (AuthApi and Settings have no sessions/devices list, no remote sign-out of other devices); backend AuthApi surface consumed by Android does not include any such endpoint.
- Cached user_json for offline restore is stored alongside tokens in the same encrypted file and wiped together, so there is no persistent, non-secret 'last account on this device' record for a Continue-as-X screen.
- usesCleartextTraffic=true and no certificate pinning on the OkHttp clients — acceptable for dev, but any device-bound-key/attestation protocol should assume TLS is the only transport protection today.
- AppLockManager preferences are per-user in plain SharedPreferences and are not backup-excluded, but that is benign; more relevant is that the app-lock decision has no tie to the auth token lifecycle (biometric success does not unlock/derive anything cryptographic).
