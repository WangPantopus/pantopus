## SUMMARY
Auth today is Supabase Auth JWTs fronted by Express. Mobile (native iOS + Android) uses Bearer transport with tokens returned in JSON; web uses httpOnly cookies set by the backend via a same-origin Next.js proxy (`x-token-transport: cookie`), with a user-bound HMAC CSRF token and a JS-readable `pantopus_session=1` flag that is a hint, never authority. Access tokens live 1h, refresh tokens rotate (Supabase `enable_refresh_token_rotation=true`, `refresh_token_reuse_interval=10`); the web refresh cookie is 7 days and path-scoped to `/api/users/refresh`. `verifyToken` calls `supabase.auth.getUser` on every request and caches role/account_type in-process for 60s. Logout is unauthenticated/no-CSRF and best-effort revokes only the presented access JWT via `admin.signOut(token,'local')`; refresh-reuse errors are logged as `auth.refresh_token_reuse`, cookies cleared, and the client gets 401 `TOKEN_REUSE`. There is no server-side session/device table, no revocation version, no "sessions on other devices" surface, and no passkey/WebAuthn code anywhere (backend, web, iOS, Android).

The docs already encode several product/security decisions a persistent-login design must respect: (1) a two-tier guard model — Tier 1 app-unlock biometric with passcode fallback, Tier 2 sensitive-action guard (strong biometric, no fallback, 5-min grace) that falls back to a server password re-auth (`POST /api/users/reauthenticate`, which returns only `{verified:true}` and does not mint any step-up/AAL claim); money surfaces are meant to be behind SensitiveScreenGuard (RN did it; native parity audit flags it missing); (2) the RN-era mobile client deliberately WIPED the Keychain session on reinstall via an AsyncStorage "install sentinel" ("prevents old sessions from silently surviving reinstall") — the exact opposite of the new goal, so the design must consciously supersede that decision; (3) the 2026-03-08 audit demanded httpOnly cookies on web (done), a real logout/revocation endpoint (done, scope local), identity-bound invites, and a "server-side session table or revocation version" if reliable cross-device revocation is required (not done); (4) email-only auth v1 (no phone OTP), soft email-verification gate; (5) native OAuth (Google/Apple) is browser-based via Supabase and `pantopus://auth/callback` (ASWebAuthenticationSession / Custom Tabs) — the native iOS app has no `com.apple.developer.applesignin` entitlement and no native Sign in with Apple; (6) privacy inventory says tokens + user id are stored in iOS Keychain with `afterFirstUnlockThisDeviceOnly` + `synchronizable=false`, Android EncryptedSharedPreferences with tokens excluded from Auto Backup and device-transfer (`allowBackup=false`) — the inventory has a change-control rule requiring the privacy labels to be updated whenever a new identifier (e.g. a device id) is collected.

Association files: the web app serves `frontend/apps/web/public/.well-known/apple-app-site-association` and `assetlinks.json` as static Next public files with `Content-Type: application/json` forced in `next.config.js`; the 2026-08-18 domain decision is that `pantopus.com`/`www.pantopus.com` is the product domain and both native apps now claim it. The AASA DOES contain a `webcredentials` block — but for appID `6UYZBA546R.com.pantopus.app`, the old Expo bundle id; the native iOS app is `app.pantopus.ios` and its entitlements declare only `applinks:` (no `webcredentials:` domain). Likewise `assetlinks.json` targets package `com.pantopus.app` with a single SHA-256, whereas the native Android `applicationId` is `app.pantopus.android`, and it lacks the `delegate_permission/common.get_login_creds` relation needed for Credential Manager/passkey/shared-credential flows. So today neither Universal Links, Android App Link verification, iOS shared web credentials/passkeys, nor Android Credential Manager can succeed for the native apps — the files must be regenerated for the native identifiers (and Play App Signing + upload cert fingerprints) as a prerequisite of any passkey/"Continue as X" design.

## FACTS
- Access JWT lifetime is 3600s (supabase/config.toml:154 jwt_expiry = 3600); refresh-token rotation on (config.toml:160) with reuse interval 10s (config.toml:163); documented in docs/interview/auth-session-security-deep-dive.md:106-111.
- Web cookies (backend/routes/users.js:392-431): pantopus_access httpOnly sameSite=lax path=/ maxAge 1h; pantopus_refresh httpOnly path=/api/users/refresh maxAge 7d; pantopus_csrf non-httpOnly 24h = HMAC(CSRF_SECRET,userId); pantopus_session non-httpOnly 30d value '1' (docs/interview/auth-session-security-deep-dive.md:140-167; docs/01-authentication-authorization.md:42-48).
- Bearer header wins over cookie; CSRF enforced only for cookie-auth unsafe methods; bearer/mobile requests skip CSRF (docs/01-authentication-authorization.md:130-163, 209-214).
- verifyToken calls supabase.auth.getUser(token) on every request and caches role/account_type in a process-local Map for 60s / 1000 entries; not distributed (docs/01-authentication-authorization.md:139-172; deep-dive:1132-1145).
- POST /api/users/refresh (backend/routes/users.js:1912-1955): mobile sends {refreshToken} in body, web uses cookie; on Supabase error matching /already used|not found/ it logs auth.refresh_token_reuse, clears cookies and returns 401 code TOKEN_REUSE (users.js:1923-1934). No server-side session record is consulted; the docs/mobile/auth-backend-contracts.md:323 claim 'all sessions terminated server-side' is Supabase's session-family revocation, not a Pantopus-side global revoke.
- POST /api/users/logout (users.js:4263) has no verifyToken and no CSRF; it clears cookies and best-effort revokes only the presented access JWT via supabaseAdmin.auth.admin.signOut(accessToken,'local') (users.js:497-503, comment: 'revokes only this access JWT (not every device)'); deep-dive:1044-1058 recommends 'a server-side session table or revocation version' for reliable cross-device revocation.

GET /api/users/auth-methods (users.js:1741) tells the client whether a password exists; POST /api/users/password (users.js:1773) requires current password; DELETE /api/users/account (users.js:3970) requires only verifyToken (no reauth on server).

## GAPS
- No server-side session/device registry: sessions exist only as Supabase refresh-token families; Pantopus cannot list, name, or revoke a specific device, cannot do 'sign out everywhere', and logout revokes only the presented access JWT (scope 'local'). The deep-dive doc already recommends a session table / revocation version.
- No device binding or proof-of-possession: refresh tokens are plain bearer secrets; a stolen refresh token wins the rotation race (deep-dive:1036-1042). Nothing ties a session to a Secure Enclave / Android Keystore key, App Attest / Play Integrity, or a device install id.
- Reinstall behavior is undefined for the native apps and contradicts prior product intent: the RN app deliberately wiped Keychain sessions on reinstall via an install sentinel; native iOS uses afterFirstUnlockThisDeviceOnly Keychain (which survives uninstall by default) with no sentinel, and Android EncryptedSharedPreferences is wiped on uninstall and excluded from backup/transfer. A persistent-login design must explicitly decide and document the reinstall/restore policy per platform and supersede docs/07 + deep-dive §7.
- Step-up/re-auth is client-local only: /reauthenticate returns {verified:true} with no server-issued step-up assertion, so sensitive endpoints (DELETE /account, payouts, password change) do not verify a recent strong auth server-side; biometric Tier-2 guard is purely client enforcement and is missing on native money surfaces (rn-functional-parity:733).
- Refresh-reuse detection is coarse ('already used' and 'not found' both logged as reuse) and reacts only by clearing cookies/401 — no user notification, no device-level revocation, no security event record (deep-dive Finding 5).
- Web and mobile session lifetimes are inconsistent and undocumented as policy: web refresh cookie 7d, pantopus_session flag 30d, mobile refresh effectively indefinite (Supabase default) — no stated max session age / inactivity timeout for either.
- Association files were written for the Expo app and never regenerated for the native apps: AASA appID 6UYZBA546R.com.pantopus.app vs native app.pantopus.ios; assetlinks package com.pantopus.app vs native app.pantopus.android. Consequently webcredentials (needed for iOS passkeys/shared web credentials/AutoFill), Universal Links, and Android App Link verification cannot succeed for the shipping native apps; iOS entitlements also lack a webcredentials:pantopus.com entry and assetlinks lacks delegate_permission/common.get_login_creds (needed for Android Credential Manager / passkeys / Smart Lock).
- No passkey/WebAuthn support anywhere (backend, web, iOS, Android); native Sign in with Apple entitlement is absent (OAuth is browser-based via Supabase), so a 'Continue as X' fast path has no phishing-resistant credential to lean on today.
- Docs are partially stale/contradictory and must be reconciled by the design: hardening-pass F8 (refresh-on-401) is now done; auth-backend-contracts §7 overstates TOKEN_REUSE as terminating all sessions; docs/01 and 07 describe RN-era storage; the release guides describe the Expo app (bundle com.pantopus.app) rather than the native apps.
- Privacy/compliance follow-through: adding a device identifier / trusted-device record or biometric-gated key requires updating docs/compliance/privacy-data-inventory.md (§6 change control) and the App Store / Play data-safety labels; Keychain flags and backup exclusions must be re-declared for any new items.
- Web session recovery gap: Next middleware clears all cookies on stale session before any refresh attempt (deep-dive Finding 1), so 'persistent login' on web is weaker than the 7-day refresh cookie implies; role cache is process-local (60s) so any revocation/trust downgrade lags.
