## SUMMARY
Pantopus's backend is a thin Express layer over Supabase Auth (GoTrue). Every credential flow (POST /api/users/login, /oauth/callback, /oauth/token, /register, /refresh) creates a per-request anon-key Supabase client (users.js:381-387, persistSession/autoRefreshToken false) and simply forwards Supabase's session. Mobile clients set no `x-token-transport: cookie` header, so `applyAuthTransport` (users.js:452-462) clears any cookies and the JSON body carries `{accessToken, refreshToken, expiresIn, expiresAt, user{...}}` (login users.js:1606-1633; oauth/callback 3927-3949; oauth/token 3859-3879, which returns only the two tokens the client itself supplied). Web gets httpOnly cookies `pantopus_access` (1h, path /), `pantopus_refresh` (7d, path /api/users/refresh), a session-bound HMAC CSRF cookie and a `pantopus_session` flag (users.js:392-433). Login is email+password via `signInWithPassword` (users.js:1500-1504); email must be confirmed (1523-1533) and a `User` row must exist (1538-1576) or the just-minted session is revoked via `revokeSessionByAccessToken` (498-528, `auth.admin.signOut(token,'local')`). OAuth supports exactly `google` and `apple` (users.js:3742); mobile obtains a provider URL with a `pantopus://` deep-link redirect (3765) and then posts either the code (/oauth/callback, `exchangeCodeForSession`) or the Supabase-issued tokens (/oauth/token, verified with `auth.getUser`). `ensureOAuthUserProfile` (647-706) creates the app profile row on first OAuth sign-in.

Refresh (users.js:1912-1958) is stateless from the backend's point of view: mobile posts `{refreshToken}` (or `refresh_token`) in the body, web relies on the path-scoped cookie (465-471); the server calls `refreshSession({refresh_token})` and returns a brand-new access+refresh pair, so rotation happens on every call because Supabase has `enable_refresh_token_rotation = true` with a 10s `refresh_token_reuse_interval` (supabase/config.toml:160-163) and `jwt_expiry = 3600` (config.toml:154). Reuse is detected only by regexing Supabase's error message (`/already used|not found/i`, users.js:1923) and answered with 401 `TOKEN_REUSE`; nothing else is revoked server-side beyond what GoTrue does. Session timebox/inactivity timeouts and MFA are all commented out or disabled (config.toml:253-257, 278-290), so a mobile refresh token never expires as long as it keeps rotating.

Per-request identity is verified by `middleware/verifyToken.js`: Bearer header wins over cookie (lines 55-61), the token is validated by a network call `supabase.auth.getUser(token)` (69, no local JWT verification, no session_id/AAL/AMR extraction), role/account_type come from a 60s in-memory cache (10-31), `req.user = {id,email,emailConfirmed,role,accountType}` (101-107) and CSRF is enforced only for cookie auth (116; middleware/csrfProtection.js:26-28). `optionalAuth` does the same with a 15s token->user cache (optionalAuth.js:16-36). Sockets authenticate with `supabaseAdmin.auth.getUser(handshake.auth.token)` (socket/chatSocketio.js:154-172). Logout (users.js:4263-4278) needs no auth: it clears cookies, takes the access token from Bearer/body/cookie (488-496) and revokes only that one session (`scope: 'local'`); there is no "sign out everywhere", "list sessions", or "revoke device" endpoint, and password change (1869) / reset (3285, 3324) never invalidate other sessions. DELETE /account (3970-4156) deletes the `User` row then `auth.admin.deleteUser` (4140), relying on cascade to drop sessions and PushToken rows.

Today there is no auth-level per-device record at all. The only device-ish table is `PushToken` (backend/database/migrations/086_push_tokens.sql, +152 for platform/provider) — `{user_id, token UNIQUE, platform, provider, created_at, updated_at}` written by POST /api/notifications/register or /push-token (routes/notifications.js:275-353) via `pushService.saveToken` upsert-on-token (services/pushService.js:37-59), removed per-token by DELETE /push-token (360-375). It has no device id, name/model, last-seen, session link, attestation, or trust state, and logout does not touch it. Rate limiting is per-IP in-memory express-rate-limit: loginLimiter 10/15m, refreshLimiter 30/15m, oauthLimiter 20/15m, reauthLimiter 10/15m, logoutLimiter 10/15m (users.js:532-578), plus authEndpointLimiter 20/min on /login and /register (app.js:297-298, middleware/rateLimiter.js:110-117) and globalWriteLimiter 30-60/min (rateLimiter.js:14-22).

## GAPS
- No per-device / trusted-device / session registry: the backend cannot enumerate, name, or revoke a specific device; PushToken is the only device-ish row and it has no device id, model, last-seen, session link, or trust state
- Refresh is bearer-only: whoever holds the refresh token can rotate it; no device binding, proof-of-possession, or attestation (App Attest / Play Integrity / DeviceCheck) on /login, /oauth/*, or /refresh
- Refresh tokens never hard-expire: [auth.sessions] timebox/inactivity_timeout are commented out (config.toml:253-257); only rotation + 10s reuse window protects them; the 7-day web cookie maxAge does not apply to mobile
- Reuse detection depends on a regex over Supabase's error text (users.js:1923) and only clears cookies; no server-side alerting, device revocation, or user notification on TOKEN_REUSE
- Logout is always scope 'local'; there is no 'sign out everywhere / other devices' route, and password change/reset (users.js:1869, 3285, 3324) do not revoke other sessions — a stolen device keeps working after the user changes their password
- DELETE /account has no step-up (no reauth, no biometric/passkey), and no explicit session/push-token revocation before deleteUser
- verifyToken does a Supabase network round-trip per request and never inspects JWT claims (session_id, aal, amr, iat), so there is nowhere today to enforce per-session/device policy, step-up (AAL2), or 'recently authenticated' checks; optionalAuth adds up to 15s revocation lag
- No MFA, passkeys, or step-up: reauthenticate is password-only and stateless (returns verified:true, mints/revokes a temp session); Supabase MFA disabled in config
- No new-device / new-login notifications (email or push) and no login audit table (ip, ua, device, geo)
- Rate limiting is per-IP in process memory (express-rate-limit MemoryStore) — no per-account lockout, no distributed store across instances, and refresh limiter (30/15min) may throttle legitimate multi-tab/app refreshes on shared IPs
- /oauth/token trusts a client-supplied refresh token without validating it pairs with the verified access token (users.js:3818-3862)
- PushToken upsert reassigns tokens across users silently (pushService.js:45-52) — fine for push, but not usable as a trust anchor; logout does not clear push tokens (removeAllTokens unused)
- Google OAuth is allowed by the backend but not configured in local supabase/config.toml (only apple), so local dev cannot exercise Google
- Two duplicate legacy helper modules (config/auth.js and middleware/auth.js) with a global signOut helper are dead code — potential confusion when adding real revocation
- Web-only CSRF/cookie protections have no mobile analogue (no device-bound key, no cert pinning signal on the server, no client attestation headers)
