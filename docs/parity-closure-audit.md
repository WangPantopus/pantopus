> Audit of the **uncommitted** WS0–WS6 "RN → Native Parity Closure" change set on `master`.
> 304 changed files, ~9.6k insertions. Generated 2026-08-05.

Method: every changed file was read (diff for modified, whole file for new) by 13 cross-platform
cluster reviewers, each finding then handed to an independent adversarial verifier instructed to
**refute** it — checking the line exists, the path is user-reachable, no guard prevents it, and
the defect is introduced by this diff rather than pre-existing. Build/lint/test gates were run for real.

**119 raw findings → 65 confirmed, 40 refuted, 14 unverified.**

### WS1.1 Auth / OAuth

- **[HIGH · correctness]** `android/app/src/main/AndroidManifest.xml:75`  
  The new OAuthCallbackActivity intent filter (AndroidManifest.xml:80-88, scheme=pantopus host=auth path=/callback) overlaps MainActivity's pre-existing scheme-only filter (lines 64-69, `<data android:scheme="pantopus"/>` with no authority). `pantopus://auth/callback?code=…` matches both: IntentFilter.matchData returns a match for a schemes-only filter regardless of authority/path. Both are exported, priority 0, DEFAULT+BROWSABLE, isDefault true. AOSP chooseBestActivity only auto-picks the top-sorted candidate when priority, preferredOrder or isDefault differ — ResolveInfo.match (filter specificity) is a sorter tiebreak but is deliberately excluded from that early-out — so with no user preference the system returns ResolverActivity and shows a disambiguation chooser with two identical "Pantopus" rows. Raising android:priority does not fix it: the parser clamps activity-filter priority to 0 for non-system apps.

Correction to the claim's wording: the default outcome is the chooser, not a silent auto-route to MainActivity. MainActivity wins only when the user taps that row — or permanently, if they tap "Always", which persists the broken mapping for every subsequent sign-in.

When MainActivity does win, the code loses the authorization code with zero fallback, and this diff is what removed the fallback. `OAuthSessionStore.deliver` has exactly one call site in the tree (OAuthCallbackActivity). Both other paths now explicitly discard the URI: MainActivity.kt:122-128 (added by this diff) early-returns on scheme/host/path, and DeepLinkRouter.kt:243-245 returns on isOAuthCallback. The awaiting coroutine in LoginViewModel.signInWithOAuth never receives a callback; onHostResumed schedules cancelIfAwaiting after 400 ms, which emits Callback.Cancelled, whose `when` branch is `Unit` — isLoading flips to false with no errorMessage. User is left on the login screen, signed out, with no explanation. Same wiring on SignUpScreen/SignUpViewModel.

Reachable via the primary "Continue with Google"/"Continue with Apple" buttons (LoginScreen.kt:175-176, 295-301); AuthApi.kt:30 hardcodes redirectTo="pantopus://auth/callback".

Fix options: (a) drop OAuthCallbackActivity and have MainActivity.forwardDeepLink call OAuthSessionStore.deliver(uri) instead of returning — a single handler, no ambiguity; or (b) keep the dedicated activity but narrow MainActivity's filter to exclude host=auth (e.g. enumerate the real content hosts), so exactly one activity matches; or (c) at minimum make MainActivity forward rather than drop, so whichever activity wins the chooser the callback still lands.  
  *Failure:* User taps "Continue with Google" on Android, completes consent, Chrome redirects to `pantopus://auth/callback?code=abc`. The system has two equal-priority handlers in the same package: it either shows a disambiguation chooser with two identical "Pantopus" rows, or routes to MainActivity, whose forwardDeepLink returns at line 126 and never calls OAuthSessionStore.deliver. The awaiting coroutine in LoginViewModel.signInWithOAuth never receives a callback; 400 ms after the next ON_RESUME it is marked Cancelled, isLoading flips to false, and the user is left on the login screen with no error and no session.
- **[HIGH · correctness]** `android/app/src/main/java/app/pantopus/android/data/auth/OAuthSessionStore.kt:67`  
  Android's new browser-OAuth flow has no CSRF state/nonce and accepts an authorization code from any app on the device. OAuthSessionStore.deliver (OAuthSessionStore.kt:67-82) validates only scheme/host/path before emitting Callback.Code, and OAuthCallbackActivity forwards any ACTION_VIEW intent data with no caller check, while AndroidManifest.xml exports that activity with a BROWSABLE pantopus://auth/callback filter (added in this diff). The only session identity is a process-local UUID minted at LoginViewModel.kt:85 (same pattern in SignUpViewModel), which never leaves the app and so cannot bind the callback to the request; AuthApi.kt:26-31 requests the provider URL with only redirectTo, and backend users.js:3862 exchanges the code with a per-request Supabase client holding no PKCE verifier, so any valid code redeems. A co-resident malicious app that fires the intent while a session is pending signs the victim into the attacker's account; because deliver() sets delivered=true on the first URI (lines 69-70), the genuine callback is then silently dropped — the same primitive also lets any app DoS a legitimate sign-in by delivering a malformed URI. Two corrections to the original report: the ownerId is minted at LoginViewModel.kt:85 (not :83), and iOS is NOT affected — OAuthWebAuthenticationCoordinator.swift:16-18 uses ASWebAuthenticationSession, where the OS delivers the callback only to the initiating session, so the cited AuthEndpoints.swift lines show a missing-state gap but no injection vector.  
  *Failure:* A malicious app watches for Pantopus to foreground a browser, then fires `startActivity(Intent(ACTION_VIEW, Uri.parse("pantopus://auth/callback?code=<code the attacker obtained for their own Google account>")))`. OAuthSessionStore.deliver accepts it (a session is pending), the ViewModel exchanges it via POST /api/users/oauth/callback, and the victim's app is signed into the attacker's account — while the real callback arriving moments later is discarded because `delivered` is already true. Any data the victim then enters (payment method, mailbox, home) lands in the attacker's account.
- **[HIGH · correctness]** `android/app/src/main/java/app/pantopus/android/ui/screens/auth/sign_up/SignUpScreen.kt:158`  
  The newly added OAuth buttons on the Create-account surface (SignUpScreen.kt:158, SignUpView.swift:40) bypass every gate the email path enforces: signInWithOAuth never runs validateAll(), never reads the accountType segment, and never checks agreedToTerms or the 18+ dateOfBirth rule. ### Token drift — measured, so it can be triaged rather than argued

iOS `verify-tokens` violations by kind: **color 16 / spacing 405 / radii 17 / typography 39** repo-wide,
and this change set contributed **zero color**. Only *color* has functional teeth: iOS tokens are
asset-catalog colors with real dark variants (`Neutral/AppText.colorset` = `#111827` light / `#E6EDF3`
dark) and dark mode is live (nothing forces `preferredColorScheme`), so a raw hex literal does **not**
flip and can render text unreadable. Android color literals are cosmetic even in principle —
`PantopusColors.appSurface` is itself a hardcoded `Color(0xFFFFFFFF)`. iOS typography drift is **not** an
accessibility issue: the tokens are fixed point sizes (`.body: 16`), so converting buys tracking and
line-height, not Dynamic Type. Conclusion: skip the spacing/radii/typography drift; detekt is the gate
that must be fixed (hard CI blocker, and its `UnusedPrivateMember` / `UnusedParameter` hits were real
dead features, not style).
